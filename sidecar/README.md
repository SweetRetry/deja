# Embedding sidecar

Local HTTP service that turns text and images into `google/embeddinggemma-2`
embeddings for the Tauri app. One process, one model in memory, serial
inference, Matryoshka truncation (normalize → slice → re-normalize) so text and
image vectors live in the same space at any supported dimension (128 / 256 /
512 / 768).

## Setup (done once, macOS arm64)

```bash
cd sidecar
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements.txt
```

`requirements.txt` pins the exact versions. `transformers==5.20.1` is the first
released line that registers the `embedding_gemma2` architecture — 5.5.x fails
with "model type `embedding_gemma2` not recognized", so no `git+` install is
needed. Weights come from the existing Hugging Face cache
(`~/.cache/huggingface/hub/models--google--embeddinggemma-2`); nothing else is
downloaded.

## Start

```bash
cd sidecar
.venv/bin/python embed_server.py --port 5187 --dim 256 --offline
```

Flags: `--port` (default `5187`), `--dim` (default `256`), `--idle-timeout`
seconds (default `180`, exits 0 when idle; `0` disables), `--offline`
(sets `HF_HUB_OFFLINE=1`, uses only cached weights), `--exit-with-stdin`
(exits when stdin closes). Listens on `127.0.0.1` only.

Only `/embed` counts as activity for the idle timeout; `/health` probes do not
keep the model alive. The app starts the model with `--exit-with-stdin` and
holds the pipe, so the model exits with the app even on a crash or `kill -9`,
and a search after an idle exit starts it again (~3 s). The app's port is 5187
unless `DEJA_MODEL_PORT` overrides it.

The process prints exactly one line to stdout once the model is loaded and the
socket is listening:

```
ready
```

Progress bars, warnings and per-request logs go to stderr. SIGTERM and SIGINT
shut the server down and exit 0; the process exit frees the model.

## HTTP contract

### `GET /health`

```json
{"ok": true, "model": "google/embeddinggemma-2", "dim": 768}
```

`dim` here is the native output dimension (768), not the truncation default.

### `POST /embed`

Request:

```json
{"items": [{"id": "a", "text": "深色登录页"}, {"id": "b", "image": "/abs/path.png"}], "dim": 256}
```

Response:

```json
{"model": "google/embeddinggemma-2", "dim": 256, "ms": 123,
 "vectors": [{"id": "a", "vector": [0.0312, ...256 floats...]}]}
```

Rules:

- `items` holds 1–8 entries; more is a `400`. Text and image items may be mixed
  in one request; each item has exactly one of `text` or `image` (mutually
  exclusive per item, no interleaved text+image input).
- `image` is a path readable by this process (absolute is safest).
- `dim` is optional and defaults to the process `--dim`; it must be an integer
  in `1..768`. Vectors are L2-normalized at 768, truncated to `dim`, then
  re-normalized, so every returned vector has norm 1 and cosine similarity is a
  dot product.
- Vectors are processed one item at a time (serial) behind a lock, so a request
  never runs inference in parallel with another.
- `ms` is the server-side wall time for the whole request.
- Errors are `{"error": "..."}` with status `400` (bad request, missing image
  file) or `500` (inference failure).

## Measured on this machine (M5-class arm64, 24 GB)

| What | Value |
| --- | --- |
| Startup, spawn → `ready` (model load + warmup, warm page cache) | ~3.0 s |
| Model load alone (`AutoModel.from_pretrained` + `.to("mps")`) | ~1.7 s |
| Peak RSS | ~1.2 GB (load-time peak); ~0.77 GB resident while idle |
| Text item, single-item request, warm | ~17 ms (p50; ~16 ms/item inside a batch of 8) |
| Image item, single-item request, warm (140×70 PNG fixture) | ~253 ms |
| Image item, 400×266 JPEG photo | ~300 ms |
| First request after `ready` | no cold-start penalty; warmup already ran |

Device selection is automatic: `mps` + `bfloat16` when Metal is available,
`cpu` + `float32` otherwise (the model card forbids `float16`). The CPU path is
slower on images (~1.2 s) and similar on text (~20 ms). Timings above were
measured while a second sidecar instance was also running, so they are if
anything conservative.

## Limits and honest gaps

- **Audio is not served.** The 300 M-parameter audio encoder is dropped at load
  (`audio_config=None`) to keep peak RSS under 4 GB; audio items are rejected by
  the request schema. Text and vision towers both load and share one space.
- **Fixture images carry no semantics.** The repo's vault images
  (`public/vault/…`, generated by `scripts/make-fixtures.mjs`) are synthetic RGB
  gradients, so image↔text cosines on them are noise — `smoke.py` prints them
  and asserts only the text-pair orderings.
- **No task prefixes.** The model card recommends text prefixes such as
  `task: sentence similarity | query: `. None are added here; callers that want
  them send them as part of `text`. Images take no prefix.
- **One image/one text per item.** Interleaved inputs (`"<|image|>"` inside a
  longer text plus several images) are supported by the model but not exposed by
  this contract.
- **Single instance.** Two servers double the memory; the app starts at most
  one per port, ties it to its own lifetime and lets `--idle-timeout` reap it.
- Image latency scales with the vision token budget fixed by the checkpoint
  (~280 soft tokens per image), not with file size.

## Proof

```bash
cd sidecar
.venv/bin/python smoke.py            # starts a server on a free port, asserts, kills it
.venv/bin/python smoke.py --image /path/to/a/real/photo.jpg
```

`smoke.py` checks `/health`, sends one request holding both an image and text
(reporting vector length, L2 norm, non-zero, and cosines), measures warm ms per
text and per image item, asserts two text orderings
(`黄昏的海边`→`日落时的海岸` beats `黄昏的海边`→`蓝色渐变按钮`, and
`深色登录页`→`暗色主题的登录界面` beats `深色登录页`→`黄色沙滩`), then kills
the server and prints its peak RSS.
